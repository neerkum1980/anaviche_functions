How the Anaviche backend is built, hosted and shipped

Four views of the same system: what calls what at runtime, which Azure resources hold it, what a single deploy does, and how a commit moves from GitHub to test and then to production. Everything here was read from the repo and the live Azure subscription on 26 September 2026.

1 · Runtime architecture

Two ways in, four APIs, two storage accounts

The browser has no function key, so it goes through gateway, which forwards the call to the real API and attaches the key for it. The MCP server holds a key and calls the APIs directly. Every API talks straight to Azure Storage; there is no database or cache in between.

FunctionRouteAuth levelReads and writes
gateway/api/gateway/{*path}anonymousNo storage. Proxies to /api/{path} and adds the key from the FUNCTIONS_KEY app setting.
PropertiesAPI/api/propertiesfunctionProperties table, one partition (PropertiesPartition). A property's id is its RowKey.
ExpenseApi/api/expensesfunctionExpenses table partitioned by property id; bill files in bills; audit JSON in audit-logs on the audit account.
BillsDownloadApi/api/BillsDownloadApifunctionReads from bills, matching on the DocumentId stored with the expense.
DocumentManagement/api/DocumentManagementfunctionPropertyDocuments table for metadata; files in property-documents under {propertyId}/.

The web frontend path is inferred from how gateway is configured: it is the only anonymous function and it injects the key. The repo does not contain the frontend itself.

2 · Deployment topology

Two resource groups, one pipeline identity

Test and production are separate Function Apps in separate resource groups, each with its own storage accounts. GitHub never holds a password: it exchanges a short-lived OIDC token for access through one Entra ID app, which can deploy to these two apps and nothing else.

3 · Deployment pipeline

What one deploy does, call by call

Each run of the deploy job follows the same sequence for test and production. All building happens on the GitHub runner. Azure never runs pip install: the app loads the zip exactly as it was uploaded, so anything missing from the zip is missing at runtime.

Smoke checkRequestPasses whenWhat it proves
PropertiesAPIGET /api/properties200Loads, reads the Properties table
ExpenseApiGET /api/expenses?propertyId=__smoke__200Loads, queries the Expenses table
DocumentManagementGET /api/DocumentManagement?propertyId=__smoke__200Loads, reaches its table and blob container
BillsDownloadApiGET /api/BillsDownloadApi400 naming documentIdLoads and runs its own validation; no storage call
gatewayGET /api/gateway/properties, no key200Proxy works and its FUNCTIONS_KEY setting is a valid key

All requests are reads, and none of them uses real data. A function with an import error answers 500, so each function returning its own expected status shows the package loaded. The whole set is retried up to 10 times while the app warms up.

  • Why dependencies are installed on the runner. Because the app mounts the zip as-is, requirements.txt is never installed on Azure. The first pipeline run skipped this step, and every function failed with ModuleNotFoundError: azure.data until the workflow was changed to ship .python_packages inside the zip.
  • What the deploy identity can touch. Website Contributor on the two Function Apps only. It reads the storage connection string from the app's settings, which is how the upload reaches the storage account.
4 · CI/CD and promotion

Every push lands in test; production waits for you

One workflow, Deploy Functions, runs both lanes. The steps are identical; only the trigger and the target change. Production can only be deployed from main, so it always runs code that has already been through test.

Test lane passing · run 36228649955

The smoke test has already paid for itself: on the first run it caught a deploy that shipped without its Python packages. That was fixed by building dependencies in CI, and test was green again one push later. Production has not been deployed through the pipeline yet.

  • If check fails, nothing is deployed and both environments keep their current code.
  • If the smoke test fails, the new code is already running; the run turns red so you know. Roll back by reverting the commit and pushing, then promoting again if production was affected.
  • One deploy per environment at a time. A second push waits for the running test deploy instead of racing it.
  • Only the Function App code ships. .funcignore keeps mcp_server/, docs/, virtual environments, local.settings.json and .git* out of the package.

Not set up yet

  • Approval on production. Anyone who can run workflows can promote. Adding required reviewers to the production environment in GitHub settings turns the manual step into an approval.
  • Staging slot swap. Production has a staging slot the pipeline ignores. Deploying there and swapping would make production releases instant and reversible.
  • Production monitoring. Only test sends telemetry to Application Insights, so production failures show up only in the smoke test.
  • Package link expiry. Each deploy points WEBSITE_RUN_FROM_PACKAGE at a zip in the app's storage account through a SAS link that expires after one year. An app that goes a year without a deploy stops loading; redeploying renews the link, and switching the app to managed-identity package access removes the expiry.
  • MCP server hosting. The MCP server runs on your machine and is excluded from deploys.
